# 1일차 개발 문제점 및 해결 과정

## 1. 목표와 초기 구조

1일차에는 공지 이미지를 입력받아 제목, 대상, 행동 항목과 일정을 추출하고 SQLite에 저장하는 기능을 구현했다. 초기 구조에서는 로컬 Vision 모델인 `qwen3-vl:4b-instruct`가 이미지 인식과 JSON 구조화를 모두 담당했다.

```text
이미지 업로드
  → Qwen3-VL 이미지 분석
  → NoticeExtraction 형식의 JSON 생성
  → 날짜 정규화
  → SQLite 저장
```

이 방식은 외부 API 없이 전체 추출 과정을 처리할 수 있다는 장점이 있었지만, 긴 공지 이미지와 복잡한 JSON 스키마를 동시에 처리하면서 안정성과 OCR 정확도 문제가 발생했다.

## 2. Qwen3-VL JSON 생성 과정의 반복 오류

### 증상

Qwen3-VL에 공지 이미지를 전달하면서 `NoticeExtraction` JSON Schema에 맞는 결과를 직접 생성하도록 요청했다. 일부 이미지에서 모델이 같은 토큰이나 문장을 반복적으로 생성하면서 응답을 끝내지 못했고, Ollama가 토큰 반복 한도 오류를 반환했다.

구조화 결과를 한 번에 생성해야 했기 때문에 모델은 다음 작업을 동시에 수행해야 했다.

- 이미지 속 작은 한글 텍스트 인식
- 표와 본문의 읽기 순서 판단
- 일정과 일반 문장의 의미 구분
- 날짜와 시간을 ISO 8601 형식으로 변환
- 중첩된 JSON Schema 준수

### 원인

4B 규모의 Vision 모델에 OCR과 복잡한 구조화를 한 번에 요구한 것이 주요 원인이었다. 특히 긴 이미지에서 인식해야 할 텍스트가 많아지면 출력 길이가 증가했고, JSON 문법과 스키마를 유지하는 과정에서 반복 생성에 빠질 가능성이 커졌다.

### 초기 대응

재시도할 때 temperature와 seed를 변경하고, 서버 오류가 발생하면 이미지 해상도를 낮추도록 구성했다. 이 방식은 동일한 반복 패턴을 피하거나 모델의 이미지 처리 부담을 줄이기 위한 대응이었다.

## 3. 이미지 리사이징 적용

반복 오류와 모델 처리 부담을 줄이기 위해 이미지의 최대 변 길이와 전체 픽셀 수를 제한했다. 원본 이미지가 설정된 한도를 넘으면 가로세로 비율을 유지한 상태로 축소한 뒤 Qwen3-VL에 전달했다.

예를 들어 `kt_01.png`는 다음과 같이 처리됐다.

```text
원본: 1071 × 3028
리사이징: 896 × 2496
```

리사이징으로 Vision 인코더가 처리해야 하는 이미지 크기는 줄었지만, 공지 하단의 작은 글자와 표 내부 텍스트도 함께 축소됐다.

## 4. 리사이징으로 인한 OCR 성능 저하

### 증상

KT DS 채용 공지에서 상단의 제목, 모집기간, 지원자격과 근무지는 인식했지만 다음 핵심 영역이 누락됐다.

- 모집분야
- SW Engineering 수행업무와 우대사항
- Cloud/Infra Engineering 수행업무와 우대사항
- Security 수행업무와 우대사항

일부 글자는 인식되더라도 비슷한 모양의 다른 한글로 잘못 변환됐다.

### 원인

원본 이미지는 세로로 긴 웹페이지 캡처이며, 모집분야 표의 글자 크기가 상단 제목보다 훨씬 작다. 전체 이미지를 축소하면서 표 내부 글자의 픽셀 정보가 줄어들었고, 모델이 큰 제목과 주요 정보에 우선적으로 집중하면서 작은 표 내용을 생략했다.

### 결과

리사이징은 모델의 처리 부담을 줄이는 데에는 도움이 됐지만, 전체 텍스트 보존이라는 OCR 목표에는 적합하지 않았다. 이후 리사이징을 제거하고 원본 해상도를 그대로 전달하도록 변경했다.

## 5. OCR과 JSON 구조화 단계 분리

Qwen3-VL이 OCR과 JSON 생성을 동시에 담당하던 구조를 두 단계로 분리했다.

```text
이미지 업로드
  → Qwen3-VL 원문 OCR
  → OCR 텍스트
  → GPT-4o-mini Structured Outputs
  → NoticeExtraction 검증
  → 날짜 정규화
  → SQLite 저장
```

Qwen3-VL은 이미지에 보이는 텍스트를 옮겨 적는 작업만 수행한다. GPT-4o-mini는 OCR 텍스트를 입력받아 Pydantic 스키마에 맞는 데이터를 생성한다. 이 구조로 변경하면서 Qwen3-VL의 JSON 반복 생성 문제를 제거하고 각 모델의 역할을 단순화했다.

## 6. 원본 해상도 전체 이미지 OCR의 한계

리사이징을 제거한 뒤 `kt_01.png`를 원본 `1071 × 3028` 크기로 전달했다. 상단과 하단의 일반 텍스트 인식량은 증가했지만, 모집분야 표는 여전히 대부분 누락됐다.

이 결과를 통해 문제의 원인이 해상도 손실만은 아니라는 점을 확인했다. 세로로 긴 이미지 전체를 한 번에 입력하면 모델이 모든 영역에 동일한 수준으로 집중하지 못하며, 가운데 위치한 작고 밀집된 표가 선택적으로 생략될 수 있었다.

## 7. 세로 분할 OCR 적용

긴 이미지 전체를 한 번에 처리하는 대신 원본 이미지를 세로 3개 구간으로 나누어 OCR하도록 변경했다.

- 각 구간은 원본 해상도를 유지한다.
- 인접 구간은 높이의 15%가 겹치도록 구성한다.
- 각 구간을 위에서 아래 순서로 OCR한다.
- 구간별 OCR은 최대 2회 시도한다.
- 모든 OCR 결과를 이미지 순서대로 병합한다.

분할 OCR 적용 후 다음 모집분야와 세부 항목을 인식할 수 있었다.

- SW Engineering
- Cloud/Infra Engineering
- Security
- 각 분야의 수행업무
- 각 분야의 우대사항

전체 이미지 OCR에서 누락되던 표가 별도 구간의 주요 내용이 되면서 인식 범위가 크게 개선됐다.

## 8. 중첩 구간의 중복 문장

### 증상

구간 경계의 텍스트 손실을 방지하기 위해 15% 중첩을 적용하면서 `지원자격`, `채용절차`와 같은 문장이 두 번 나타났다.

### 원인

동일한 영역을 두 구간에서 각각 OCR하므로 같은 문장이 반복된다. 두 결과가 완전히 동일하면 코드로 제거할 수 있지만, 한쪽에서는 `이내`, 다른 쪽에서는 `이후`처럼 다르게 인식되는 경우 단순 문자열 비교로 중복을 판단할 수 없었다.

### 해결

원본 OCR 결과는 증거 데이터로 보존하고, GPT-4o-mini가 다음 작업을 수행하도록 역할을 확장했다.

- 중첩 구간에서 반복된 문장 정리
- 메뉴와 웹페이지 푸터 제거
- 문맥상 명백한 OCR 오탈자 보정
- 불확실한 내용은 추측하지 않고 OCR 표현 유지

## 9. 구조화 과정에서 OCR 원문이 생략되는 문제

### 증상

초기 하이브리드 구조에서는 화면에 표시되는 `raw_text`도 GPT-4o-mini가 생성했다. Ollama가 표 내용을 읽었더라도 GPT가 중요도가 낮다고 판단한 문장을 생략하면 저장된 원문에서 해당 내용이 사라졌다.

### 해결

원본 OCR과 정리된 텍스트를 분리했다.

- `raw_text`: 분할 OCR 결과를 병합한 원본 증거
- `cleaned_text`: 중복과 명백한 오탈자를 정리한 전체 공지문

`raw_text`는 GPT 출력으로 대체하지 않고 Ollama OCR 결과를 그대로 저장한다. 화면에는 `cleaned_text`를 기본으로 표시하고, 사용자가 원본 OCR을 별도로 펼쳐 확인할 수 있도록 구성했다.

## 10. 채용 분야 구조화 스키마 부재

### 증상

기존 `NoticeExtraction`에는 제목, 대상, 해야 할 일, 신청 방법과 일정만 있었다. OCR이 모집분야 표를 읽어도 분야별 수행업무와 우대사항을 구조적으로 저장할 위치가 없었다.

### 해결

다음 구조를 추가했다.

```text
RecruitmentPosition
  ├─ name
  ├─ responsibilities[]
  └─ preferred_qualifications[]
```

SQLite에는 `notice_recruitment_positions` 테이블을 추가했다. 화면에서도 모집분야별 수행업무와 우대사항을 구분해 표시한다. 채용 공지가 아닌 일반 공지는 빈 배열을 사용해 기존 공지 처리 방식과 함께 사용할 수 있다.

## 11. 날짜 없는 채용절차가 일정으로 생성되는 문제

### 증상

서류전형, 코딩테스트, 면접, 합격발표와 같이 날짜가 적히지 않은 채용절차를 GPT가 각각 일정으로 생성했다. 이 때문에 여러 일정에 대해 다음 검증 메시지가 표시됐다.

```text
일정의 날짜를 확정할 수 없습니다.
```

### 해결

구조화 프롬프트에 다음 조건을 추가했다.

- 날짜가 명시되지 않은 채용절차 단계는 event로 생성하지 않는다.
- 날짜가 명시된 일정만 event로 생성한다.
- 지원·신청·모집 기간은 하나의 `application_deadline` event로 생성한다.
- 기간의 시작일은 `start_at`, 종료일은 `end_at`에 저장한다.

## 12. 날짜 범위 정규화 문제

### 증상

원본 OCR에 다음과 같이 날짜가 명확히 있어도 ISO 8601 값으로 변환되지 않는 경우가 있었다.

```text
지원 기간
2026년 10월 07일(수)~2026년 10월 21일(수)
```

기존 정규화 코드는 단일 한글 날짜를 중심으로 구현되어 날짜 범위, 점 표기, 종료 날짜의 연도·월 생략을 충분히 처리하지 못했다.

### 해결

날짜 정규화 코드에서 다음 형식을 직접 처리하도록 확장했다.

- `2026년 10월 07일(수)`
- `2026.10.07(수)`
- `10.07(수)`
- `2026년 10월 07일(수) ~ 2026년 10월 21일(수)`
- `2026.10.07 ~ 10.21`
- `2026년 10월 7일부터 21일까지`

시간이 명시되지 않은 기간은 다음과 같이 정규화한다.

```json
{
  "start_at": "2026-10-07T00:00:00+09:00",
  "end_at": "2026-10-21T23:59:59+09:00"
}
```

시간이 명시된 경우에는 원문에 있는 시간을 유지한다.

## 13. 원문에 없는 행동 표현 생성

### 증상

원본에는 `지원하기`와 `지원 기간`이 각각 표시되어 있었지만, GPT가 `지원 기간 동안 지원하기`라는 새로운 문장을 만들어 `action_required`에 저장했다.

### 원인

모델이 행동과 기간 정보를 자연어로 결합하면서 원문에 없는 표현을 생성했다.

### 해결

`action_required`에는 `지원하기`, `신청하기`, `제출하기`처럼 원문에 명시된 행동만 복사하도록 제한했다. 기간과 목적을 임의로 덧붙이지 않도록 프롬프트를 수정했으며, 지원 기간은 행동이 아니라 일정 데이터로 분리했다.

## 14. 최종 구조

1일차 문제를 반영한 최종 처리 흐름은 다음과 같다.

```text
이미지 업로드
  → 원본 이미지 세로 3구간 분할(15% 중첩)
  → Qwen3-VL 구간별 OCR
  → OCR 결과 병합 및 raw_text 보존
  → GPT-4o-mini 중복·오탈자 정리
  → 공지·일정·채용 분야·기타 중요 정보 구조화
  → 코드 기반 날짜 범위 정규화
  → Pydantic 검증
  → 사용자가 구조화 결과 확인 및 오류 수정
  → SQLite 저장
  → 정리문과 원본 OCR을 화면에서 구분해 표시
```

## 16. 남은 한계

- 작은 한글 글자는 원본 해상도와 분할 OCR을 사용해도 일부 오인식될 수 있다.
- 서로 다르게 인식된 중첩 문장은 원본 OCR에서 완전히 제거하기 어렵다.
- GPT의 오탈자 보정 결과는 원문과 대조할 수 있도록 검토 과정이 필요하다.
- 분할 OCR은 Qwen3-VL 호출 횟수가 증가하므로 전체 처리 시간이 길어진다.
- 채용 공지 외의 다양한 표 형식에 대해서는 추가 샘플 평가가 필요하다.

따라서 원본 OCR을 증거로 보존하고, 정리된 텍스트와 구조화 결과를 별도로 제공하는 현재 방식이 정확성과 검토 가능성 사이의 균형에 적합하다.

## 17. 기존 스키마에 속하지 않는 중요 정보 누락

### 증상

공지에는 일정과 모집 분야 외에도 우대 자격증, 제출서류, 합격 취소 조건, 수습기간과 기타 유의사항처럼 사용자가 확인해야 할 정보가 포함된다. 기존 스키마에는 이러한 정보를 저장할 전용 필드가 없어 `cleaned_text`에만 남거나 구조화 결과에서 생략될 수 있었다.

### 해결

다음과 같은 `AdditionalInformation` 구조를 추가했다.

```text
AdditionalInformation
  ├─ category
  ├─ title
  ├─ items[]
  ├─ evidence_text
  ├─ confidence
  └─ needs_review
```

카테고리는 `우대 자격증`, `제출서류`, `불이익 조건`, `유의사항`, `기타`로 분류한다. OCR 오류나 의미가 불확실한 정보는 `needs_review`로 표시하고 판단 근거가 된 원문을 `evidence_text`에 보존한다. 공백과 대소문자 차이로 반복된 항목은 저장 전에 제거한다.

SQLite에는 `notice_additional_information` 테이블을 추가했으며, 추출 결과와 저장된 공지 화면 모두에서 `기타 중요 정보` 영역을 별도로 표시하도록 변경했다.

## 18. 저장 과정의 재추출로 결과가 달라지는 문제

### 증상

최초 추출 화면에는 `기타 중요 정보`가 표시됐지만 저장된 공지에서는 해당 정보가 사라지는 현상이 발생했다.

### 원인

프론트엔드는 화면에 표시된 `extraction`을 저장 요청에 포함했지만, 서버의 등록 요청 스키마가 이 필드를 받지 않아 값을 무시했다. 이후 `/notices/register`가 같은 이미지를 다시 Ollama와 OpenAI에 전달해 재추출했다. 생성형 모델의 두 번째 결과가 첫 번째 결과와 달라질 수 있어 일부 정보가 사라졌으며, 저장할 때마다 모델 API 비용과 처리 시간도 추가됐다.

### 해결

등록 API가 프론트엔드에서 전달한 `NoticeExtraction`을 Pydantic으로 검증한 뒤 그대로 저장하도록 변경했다.

```text
기존: 이미지 분석 → 결과 확인 → 저장 요청 → 이미지 재분석 → 저장
변경: 이미지 분석 → 결과 확인 → 검증된 추출 결과 저장
```

저장 단계에서는 Ollama와 OpenAI를 다시 호출하지 않는다. 따라서 화면에서 확인한 모집 분야와 기타 중요 정보가 동일하게 저장되고, 불필요한 API 사용료와 대기 시간이 발생하지 않는다.

## 19. OCR 및 구조화 오류를 사용자가 수정할 수 없는 문제

### 증상

OCR과 GPT 구조화 결과에 글자 오인식, 잘못된 날짜, 누락된 항목이 있어도 기존 화면에서는 결과를 읽고 저장하는 것만 가능했다. 오류를 발견하면 이미지를 다시 분석해야 했지만 재추출해도 정확히 수정된다는 보장이 없었다.

### 해결

추출 결과에 저장 전 편집 모드를 추가했다. 사용자는 다음 항목을 직접 수정할 수 있다.

- 제목, 대상, 해야 할 일, 신청 방법
- 일정 종류, 날짜 문구, 시작·종료 일시, 장소, 종일 여부
- 모집 분야, 수행업무, 우대사항
- 기타 중요 정보의 분류, 제목, 내용, 검토 필요 여부
- 정리된 전체 텍스트

일정, 모집 분야와 기타 중요 정보는 새로 추가하거나 잘못 생성된 항목을 삭제할 수 있다. 배열 데이터는 한 줄에 한 항목씩 편집하도록 구성했다.

`수정 취소`를 누르면 편집 전 추출 결과로 복원되고, `수정 완료` 후 저장하면 수정된 구조화 결과가 등록 API로 전달된다. 저장 중 모델 재추출이 없으므로 사용자가 수정한 내용이 그대로 SQLite에 저장된다.

원본 증거가 사용자 수정으로 바뀌지 않도록 `raw_text`와 각 항목의 `evidence_text`는 읽기 전용으로 유지한다. 사용자가 새로 추가한 일정이나 기타 정보는 OCR 근거가 없을 수 있으므로 저장 전 검토가 필요하다.
