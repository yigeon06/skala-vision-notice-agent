# Vision 기반 공지·일정 관리 Agent

공지 이미지를 읽어 저장하고, 자연어 검색과 달력으로 필요한 내용과 날짜를 확인하는 로컬 웹 애플리케이션입니다.

## 1. 프로젝트명 및 주제 선정 배경

사진이나 캡처로 전달된 공지는 제목·신청 방법·마감일·행사일을 사용자가 직접 읽고 옮겨 적어야 합니다. 공지가 쌓이면 필요한 내용을 다시 찾기 어렵고, 신청 마감과 실제 행사 날짜를 혼동하기 쉽습니다. 이 프로젝트는 이미지 속 정보를 검색 가능한 공지와 일정으로 바꾸기 위해 시작했습니다.

## 2. 해결하고자 하는 문제

- 이미지에 흩어진 제목, 대상, 신청 방법, 일정과 채용 분야 정보를 한곳에 보관합니다.
- 신청·제출 마감과 행사·발표 일정을 구분해 날짜별로 조회합니다.
- 저장한 공지를 기간·상태 조건 또는 내용으로 찾고, 원문 근거를 확인합니다.
- 추출 결과가 불확실할 때 사용자가 저장 전에 확인·수정할 수 있게 합니다.

## 3. 개발 환경 및 기술 스택

| 영역             | 기술                           | 역할                                                    |
| ---------------- | ------------------------------ | ------------------------------------------------------- |
| 프론트엔드       | Vue 3, Vite                    | 채팅, 이미지 등록·수정, 검색 결과, 공지 상세, 월간 달력 |
| 백엔드           | Python, FastAPI, Pydantic      | API, 입력·추출 결과 검증                                |
| Agent            | LangGraph                      | 일반 대화·공지 등록·공지 조회 경로 제어                 |
| 이미지 읽기      | Ollama `qwen3-vl:4b-instruct`  | 이미지를 나눠 OCR 수행                                  |
| 정보 구조화·답변 | OpenAI `gpt-4o-mini`           | Structured Outputs 추출, 일반 대화와 근거 기반 답변     |
| 저장·검색        | SQLite, Ollama `bge-m3`, NumPy | 공지·일정·임베딩 저장, 조건 검색과 벡터 유사도 계산     |
| 추적·검증        | LangSmith(선택), pytest        | 실행 추적, 모의·회귀 테스트                             |

실행에는 Python, Node.js/npm, Ollama, OpenAI API 키가 필요합니다. 모델과 임베딩 설정은 [`.env.example`](./.env.example)을 기준으로 변경할 수 있습니다. LangSmith 추적은 선택 기능입니다.

## 4. 시스템 아키텍처

```mermaid
flowchart TD
    UI["Vue 화면"] --> API["FastAPI"]
    API --> AG["LangGraph /agent"]
    AG --> CHAT["일반 대화: OpenAI"]
    AG --> REG["공지 등록"]
    AG --> SEARCH["공지 조회"]
    REG --> OCR["Ollama Vision OCR"]
    OCR --> STRUCT["OpenAI 구조화"]
    STRUCT --> VALID["Pydantic·날짜 검증"]
    VALID --> EDIT["사용자 확인·수정"]
    EDIT --> DB[("SQLite 공지·일정·임베딩")]
    SEARCH --> SQL["기간·상태·일정 유형: SQL"]
    SEARCH --> RAG["내용 질문: 벡터 검색·근거 답변"]
    SQL --> DB
    RAG --> DB
    API --> CAL["월간 달력 API"]
    CAL --> DB
```

이미지가 첨부되면 등록 경로로 이동합니다. 텍스트 질문은 자동 분류하거나 사용자가 화면에서 `공지/일정 조회`, `세부 내용 조회`를 선택할 수 있습니다. 선택한 검색 방식은 화면을 새로고침할 때까지 유지됩니다. 두 검색 방식은 각각 SQLite 조건 검색과 임베딩 기반 의미 검색을 사용합니다.

공지 한 건에는 여러 일정, 채용 분야, 기타 중요 정보, 검색용 청크가 연결됩니다. 이미지는 로컬 파일에, 구조화 데이터와 청크·임베딩은 SQLite에 저장합니다. 일정 추출 스키마는 일정 유형·원문 날짜·시작일·종료일·장소·근거 문장의 여섯 항목이며, 날짜는 `YYYY-MM-DD` 단위로 다룹니다. 기존 DB의 일시 열에는 서울 시간 기준 시작일 00:00:00과 종료일 23:59:59가 기록되지만, 이를 실제 시각으로 해석하지 않습니다.

## 5. 주요 구현 기능

- **이미지 등록:** PNG·JPG·WEBP 이미지(최대 10MB)를 업로드합니다. 이미지를 세로 세 구간으로 나눠 OCR하고, 구조화 결과를 검증합니다. 보완 가능한 누락에는 구조화 단계만 최대 한 번 재시도합니다.
- **저장 전 검토:** 제목, 대상, 본문, 해야 할 일, 신청 방법, 일정, 모집 분야와 기타 중요 정보를 수정한 뒤 저장합니다. 원본 OCR과 근거 문장은 확인용으로 보존합니다. 요청 ID로 중복 저장을 방지합니다.
- **공지 검색:** 기간·상태·일정 유형은 SQLite로 조회합니다. 내용 질문은 저장한 청크의 임베딩 유사도로 공지를 찾고, 근거에 기반한 답변과 출처를 표시합니다.
- **월간 달력:** 저장된 일정의 월별 목록을 보여줍니다. 모든 기간 일정은 시작일과 종료일에만 표시하고, 같은 공고의 같은 날짜에 겹치는 신청·제출 일정은 한 항목으로 묶습니다. 참여후기처럼 참여 기간으로 확인되는 이벤트는 달력에서 ‘참여 시작·마감’으로 표시합니다. 날짜가 확정되지 않은 일정은 별도 목록에 나타납니다.
- **상세 화면:** 정리문과 원본 OCR, 일정, 채용 분야별 수행업무·우대사항, 기타 중요 정보를 확인합니다.

주요 API는 `POST /agent`, `POST /images`, `POST /notices/extract`, `POST /notices/register`, `GET /notices`, `GET /notices/{notice_id}`, `GET /calendar/events`입니다. `POST /chat`도 호환용으로 제공됩니다.

## 6. 프로그램 실행 방법

프로젝트 루트에서 아래 명령을 실행합니다.

```bash
bash sh/setup_venv.sh
bash sh/setup_ollama.sh
cp .env.example .env
npm install --prefix frontend
```

`.env`에 실제 `OPENAI_API_KEY`를 입력합니다. `sh/setup_ollama.sh`는 기본 Vision 모델과 임베딩 모델을 준비합니다. 이후 터미널 두 개에서 실행합니다.

LangSmith를 사용하려면 `.env`에 `LANGSMITH_TRACING=true`, 실제 `LANGSMITH_API_KEY`, 원하는 `LANGSMITH_PROJECT`를 설정합니다. 이전 설정의 `LANGCHAIN_TRACING_V2`·`LANGCHAIN_API_KEY`·`LANGCHAIN_PROJECT`도 읽지만 새 변수 사용을 권장합니다. 서버는 추적이 켜지면 입력·출력 숨김을 강제합니다. LangSmith에는 등록·검색·대화의 단계, 실행 시간, 오류 상태, 모델명과 토큰 사용량 등만 기록하며 이미지, OCR 원문, 공지 내용, 질문·답변 본문은 보내지 않습니다. 실제 추적을 확인하려면 키를 설정한 뒤 서버를 다시 시작하고 요청을 실행해 LangSmith 프로젝트를 확인합니다. 키와 `.env`는 Git에 올리지 않습니다.

```bash
# 터미널 1: 백엔드
bash sh/run_agent_ollma.sh
```

```bash
# 터미널 2: 프론트엔드
bash sh/run_frontend.sh
```

브라우저에서 `http://127.0.0.1:5173`을 엽니다. 백엔드 기본 주소는 `http://127.0.0.1:8100`입니다. 공지 이미지를 첨부해 추출 결과를 확인·수정한 뒤 저장하거나, 저장된 공지를 사이드바·달력·채팅 검색으로 조회할 수 있습니다. 대화 이력은 화면 메모리에만 남아 새로고침하면 초기화되며, 저장한 공지는 SQLite에 유지됩니다.

## 8. 개발 과정의 문제점 및 해결 방법

- **이미지 OCR의 반복·누락:** 분할 OCR과 반복 텍스트 정리를 적용하고 원본 OCR을 함께 보관했습니다. 읽기 어려운 원본은 여전히 수동 검토가 필요합니다.
- **마감 유형 혼동:** 예를 들어 ‘신청 마감’이 제출 마감으로 추출되면 기간 검색에서 빠질 수 있습니다. 원문의 명확한 표현과 일정 유형이 충돌할 때 검증 오류로 처리하고 구조화 재시도를 연결했습니다.
- **날짜 표현의 다양성:** 한글·점 표기와 기간 표현을 `YYYY-MM-DD`로 정규화하고 시작일·종료일 순서를 검증합니다. 시각은 추출 스키마에서 제외하고 원문 문구와 근거에 남깁니다.
- **중복 등록:** 동일 요청 ID에 고유 제약을 적용하고 저장 실패 후 재시도에도 같은 ID를 사용합니다.
- **질문 분류의 모호성:** 자동 분류 외에 검색 방식 선택 버튼을 제공했습니다. 이는 경로 선택을 돕지만, 주제만 언급한 질문에서 관련 없는 공고가 나오는 문제까지 해결하지는 못했습니다.

상세한 개발 기록은 [1일 차 이슈](./docs/day1_issues.md), [2일 차 이슈](./docs/day2_issues.md)에서 확인할 수 있습니다.

## 9. 한계점 및 향후 개선 방향

- 실제 공고 여러 건을 대상으로 현재의 **날짜 전용 스키마**와 검색 품질을 다시 평가해야 합니다. 과거 평가 결과를 현재 성능으로 간주하지 않습니다.
- SQL 조건 검색은 주제 키워드를 충분히 제한하지 못해 무관한 공고가 나올 수 있습니다. 의미 검색도 관련 청크가 상위 후보에 들지 않으면 답을 놓칠 수 있어 검색·재순위화 개선이 필요합니다.
- 날짜만 구조화하므로 같은 날의 정확한 마감 시각을 비교하거나 알림을 보내지는 못합니다. 시각이 중요한 공지는 원문을 확인해야 합니다.
- OCR 오독과 모호한 날짜는 자동으로 완전히 교정되지 않습니다. 저장된 기존 공지의 잘못된 일정은 사용자가 확인해야 합니다.
- 현재는 단일 사용자 로컬 프로토타입입니다. 계정, 접근 제어, 다중 사용자 운영 기능은 구현 범위에 포함되지 않았습니다.
